# ランダム対戦のレーティング

会員の初期レート・初期最高レートは1000。既存会員にも同じ初期値を設定し、過去の対戦からは計算し直しません。マッチングはレート差を一切制限しません。3本先取を1試合として扱い、ラウンドごとの加算はしません。

勝つと上がり、負けると下がる仕組みは、[セガのぷよぷよテトリス2S公式マニュアル](https://manual.sega.jp/puyopuyotetris2/S/jp/)を参考にしています。同作の計算式を再現したものではありません。

## 計算式

報告者は最初の結果報告時、未報告の相手は勝敗確定時のD1上のレートを使い、敗者のレートから勝者のレートを引いた値を `d` とします。

```text
増減幅 = round(24 + 20 × d / (400 + abs(d)))
勝者の新レート = 現在レート + 増減幅
敗者の新レート = max(0, 現在レート - 増減幅)
最高レート = max(これまでの最高レート, 新レート)
```

同格では24点。400点上の相手に勝つと34点、400点下の相手に勝つと14点。独自の滑らかな有理関数で、格上への勝利ほど増加し、極端な差でも4〜44点の範囲に収まります。敗者が0点付近の場合は減少だけを0で止め、勝者の加点は維持します。連勝・圧勝・切断に追加係数は付けません。

対戦者の両方が会員の場合だけ増減します。片方でもゲストなら両者とも増減0で、最高レートとレート対象試合数も変わりません。ゲストはレートの代わりに `GUEST` を表示します。ルーム対戦はレート対象外です。

## 結果と切断

ランダム対戦もWebRTC DataChannelでブラウザー同士を接続し、ホストのブラウザーが共通ゲームエンジンを60Hzで実行します。入力と盤面はP2Pで送受信し、CloudflareのDurable Objectsには接続しません。ゲスト側の入力予測とACK補正も継続します。

- 3本先取の決着時、双方が `POST /api/v1/records/random` に試合ID・自分の席・勝敗・相手のアカウントIDを送ります。サーバーはCookieで報告者本人を確認します。参加者のIDはランダム対戦のP2P接続時に共有します（認証用のCookie・パスワードは共有しません）。
- 最初の報告から5秒以内に双方が報告すれば、先に届いた報告の勝敗で確定します。食い違った場合も先着を採用します。同じ受信時刻の場合は0番席を優先します。
- **5秒経っても片方しか報告していなければ、報告したプレイヤーの勝ちです。** 報告が敗北を申告していても、単独報告のルールを優先します。対戦相手の戦績・レートも同時に更新します。
- 「退室する」を押した場合は退室側も敗北を報告します。ゲスト側はホストへの再接続を10秒試み、復帰しない場合は勝利を報告します。ホスト側はゲストの切断を検知した時点で勝利を報告します。通常決着後の切断はゲーム上の勝者を変えません。対戦前のキャンセルは集計対象外です。
- 確定した勝敗・参加者・計算用レートを `random_decisions` に保存します。後から異なる報告が届いても確定結果を返し、覆しません。同一試合の両席を同一アカウントで報告することは禁止します。
- 両者の戦績・現在値・最高値・対象試合数はD1のバッチで保存し、`(user_id, match_id)`と適用済みフラグで二重加算を防ぎます。DB障害時も保存済みの確定結果から再試行できます。
- 待機中はHTTP 202です。ブラウザーは500ms・1500ms・3000msの間隔で最大3回再確認します。ページを閉じた場合も、毎分のWorker定期処理が受信済みの報告を確定します（1回最大100試合、超過分と失敗分は次回へ）。従来のセッション清掃は毎時のままです。定期処理もDOを使いません。
- 送信そのものに失敗した場合はマイページから再送できます。未送信の情報はタブを閉じると失われます。旧v8の未確定報告は相手IDがないことがあり、その場合は報告者の勝利だけを保存してレートは変更しません。

試合中のレート表示はP2Pで共有する参考値です。計算にはD1上の値だけを使います。ホストの改変、虚偽の勝利申告、相手IDの偽装は検証しない運用です。片側の報告でも勝敗を確定する方針を優先します。

## 公開と互換性

`0008_random_decisions.sql`で相手ID・確定結果・再試行状態を追加します。既存の確定済み戦績は移行時に確定結果へ取り込み、変更しません。公開ワークフローはDB migration→API→Pagesの順に適用します。旧 `GET /api/v1/random/:code` はHTTP 410でページ更新を案内し、DOを起動しません。既存のDOクラス・binding・migrationは旧データを破壊せず移行するために残しています。

相手の探索・コード交換はPeerJS仲介を使います。通信プロトコルはv9で、古いクライアントとは接続・待機列を分離します。APIのないGitHub Pages版はP2Pのゲスト対戦で、レート・永続戦績を利用できません。結果保存あり／なしの待機列も分けます。新たな有料プランや外部サービスの契約は不要です。
