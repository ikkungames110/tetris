# ランダム対戦のレーティング

会員の初期レート・初期最高レートは1000。既存会員にも同じ初期値を設定し、過去の対戦からは計算し直しません。マッチングはレート差を一切制限しません。3本先取を1試合として扱い、ラウンドごとの加算はしません。

勝つと上がり、負けると下がる仕組みは、[セガのぷよぷよテトリス2S公式マニュアル](https://manual.sega.jp/puyopuyotetris2/S/jp/)を参考にしています。同作の計算式を再現したものではありません。

## 計算式

各プレイヤーの最初の結果報告時に保存したレートを使い、敗者のレートから勝者のレートを引いた値を `d` とします。

```text
増減幅 = round(24 + 20 × d / (400 + abs(d)))
勝者の新レート = 現在レート + 増減幅
敗者の新レート = max(0, 現在レート - 増減幅)
最高レート = max(これまでの最高レート, 新レート)
```

同格では24点。400点上の相手に勝つと34点、400点下の相手に勝つと14点。独自の滑らかな有理関数で、格上への勝利ほど増加し、極端な差でも4〜44点の範囲に収まります。敗者が0点付近の場合は減少だけを0で止め、勝者の加点は維持します。連勝・圧勝・切断に追加係数は付けません。

双方が結果報告時にログイン済みの会員で、勝敗報告が一致した場合だけ増減します。片方でもゲストなら両者とも増減0で、最高レートとレート対象試合数も変わりません。ゲストはレートの代わりに `GUEST` を表示します。ルーム対戦はレート対象外です。

## 結果と切断

ランダム対戦もWebRTC DataChannelでブラウザー同士を接続し、ホストのブラウザーが共通ゲームエンジンを60Hzで実行します。入力と盤面はP2Pで送受信し、CloudflareのDurable Objectsには接続しません。ゲスト側の入力予測とACK補正も継続します。

- 3本先取の決着時、双方が `POST /api/v1/records/random` に試合ID・自分の席・勝敗を送ります。サーバーはCookieの本人確認を行い、双方の勝者が一致してから戦績・レートを保存します。アカウントIDは対戦相手に送信しません。
- 対戦中に「退室する」を押した場合は、退室側も敗北を報告します。双方の報告が届けば保存します。通常決着後の退室は勝者を変更しません。
- 突然のタブ終了・回線断にはP2Pの10秒の復帰猶予があります。片方の報告しか届かない場合や勝敗が一致しない場合は、戦績・レートを確定しません。待機キャンセルも集計対象外です。
- `random_reports` は試合ID・席で一意、同一試合で同一アカウントが両席を報告することも禁止します。最初の報告の参加者・勝敗・レートは上書きできません。
- D1のバッチで両者の戦績、現在値、最高値、対象試合数をまとめて保存します。`(user_id, match_id)`と適用済みフラグで重複加算を防ぎます。失敗時も同じ報告を再送できます。
- 相手の報告待ちはHTTP 202です。ブラウザーは500ms・1500ms・3000msの間隔で最大3回だけ再確認し、その後はマイページから手動で再送・確認します。通信失敗も手動再送できます。未送信の情報はタブのメモリーに保持するため、閉じると失われます。サーバーが受信済みの報告はD1に残ります。

試合中のレート表示はP2Pで共有する参考値です。レート計算にはD1上の値のみを使い、結果画面にはAPIから受け取った確定値を表示します。ホストの改変や双方の共謀による架空の試合までは検証しません。また、敗者が報告しなければ未確定のままになる設計です。

## 公開と互換性

`0007_random_reports.sql`を追加します。公開ワークフローはDB migration→API→Pagesの順に適用します。旧 `GET /api/v1/random/:code` はHTTP 410でページ更新を案内し、DOを起動しません。既存のDOクラス・binding・migrationは旧データを破壊せず移行するために残しています。

相手の探索・コード交換はPeerJS仲介を使います。通信プロトコルはv8で、古いクライアントとは接続・待機列を分離します。APIのないGitHub Pages版はP2Pのゲスト対戦で、レート・永続戦績を利用できません。結果保存あり／なしの待機列も分けます。新たな有料プランや外部サービスの契約は不要です。
