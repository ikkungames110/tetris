# テンプレート連携の検知

## developのデバッグ表示

盤面上の簡単な「DEBUG / 最終検知」欄に、初期形が一致した時点で`DT canon / 状態1 検知`とプレイヤー・左端の列・上端の行・反転の有無を表示する。指定のDoubleを消した後に次の地形が一致すると、`DT canon / 状態2 検知`に更新する。行・列は画面左上を1として数える。操作中のミノは照合に含めない。

別の行の消去などで検知位置が変わった場合も表示を更新する。消去後も最後の検知を残し、ゲーム開始・リセット・新ラウンドで`未検知`に戻す。「最終検知」は履歴なので、形がなくなっても表示は残る。形の検知だけではボイスは再生しない。

デバッグ欄は固定盤面または連携の段階が変わった時だけ再計算し、同じ内容のオンラインスナップショットでは走査を省略する。

`develop`の変更は`main`のみを対象とする本番公開ワークフローでは公開されない。ローカルで`npm run dev`を実行して確認する。

## Double→Tripleの成立判定

`src/templete/DT canon/DT canon_new.json`の`states`を配列順に使う。各状態には地形と、その状態を消すTミノの位置をまとめて記述する。

1. 状態1（5列×7行）の必要ブロックを検知する。
2. 状態1の`2`と一致する位置・向きにTを固定し、**下から2・3行目**をFull T-spin Doubleで消す。
3. 消去による移動後の同じ位置・向きに状態2（4列×5行）の必要ブロックがあることを確認し、次の段階へ進む。
4. 状態2の`2`と一致する位置・向きにTを固定し、**下から1・2・3行目**をFull T-spin Tripleで消したら、「DT canon」の文字・ボイスを出す。

下からの行番号は、各形の最下行を1とする。20行JSONではDoubleが17・18行目、Tripleが17・18・19行目に相当する（こちらは0始まり）。状態2だけを組んでも、先行する指定のDoubleの記録がなければDT canon演出にはならない。

Doubleは通常の「T-SPIN DOUBLE」、Tripleの消去SEは通常のものを残す。エンドレス・40LINE・オンライン両席・リプレイに対応する。Perfect Clearが成立する場合は従来どおりそちらを優先する。

## 形の照合と位置の追跡

- `cellTypes.gray`（このJSONでは`1`）は色に関係なく必要な固定ブロック。`cellTypes.t`（`2`）はこれから入れるTの4マスで、固定前は空き必須。各状態の灰色とTを囲む矩形の内側（左右の端列を除く）にある`cellTypes.empty`（`0`）も空き必須にする。矩形の端列の`0`と矩形外の追加ブロックは許可する。これにより状態1は11マス、状態2は7マスの入口・内部の空間を、座標の別途指定なしで確認する。
- Tの4マスすべての位置、Full T-spin判定、Tがある行すべての消去が一致した場合にだけ段階を進める。消去後の次状態の地形と空間も確認する。
- 左右移動・高さの違い・左右反転に対応する。段階ごとの幅が違っても、両形を含む共通の幅を基準に反転する。状態2は初期形より右端1列が狭いため、反転時は表示する左端が1列右へ移る。
- **毎設置、消去後の固定盤面を走査して初期形の場所を更新する。** 発火時は消去前の盤面から今回固定したミノを除き、初期形を再確認する。
- Double後は位置・向き・段階を保持し、毎設置その位置の状態2を再確認する。消去しない設置は許可し、必要なブロックと内部の空間が残っていれば保持する。
- 形全体の上側・下側にある別の行を消しても段階を解除せず、消去による行のずれを補正する。形の範囲内で指定外の行を消した場合や、指定行をFull T-spin以外で消した場合は次段階の候補を解除する。
- おじゃまのせり上がりでも位置を補正し、新ラウンドでは解除する。
- 同時追跡は最大32候補／プレイヤーで、Double後の候補を優先する。発火時の初期形の再検知はこの保存件数の上限に依存しない。テンプレート登録数自体の上限ではない。

表示・音声の情報だけを追加し、攻撃力や乱数・勝敗判定には使わない。候補と成立名はオンラインの検証済みスナップショットで共有し、既存リプレイの状態ハッシュからは除外する。初期形の段階も共有するため、通信プロトコルはバージョン4に更新した。

報告画像の盤面を`tests/fixtures/dt-false-positive.json`に転記して検証している。旧条件では「左2列目・上14行目」で誤検知したが、内部の空間を確認する条件では候補にならない。Double→Tripleの成立テストも、各段階の型の内部にTミノを入れる実配置を使用する。

## テンプレートの追加

1. `src/templete/<表示名>/`に新形式のJSONを1枚置く。専用ボイスを使う場合は同じフォルダーにMP3も置く。PNGは不要。
2. JSONは`name`、`width: 10`、`height: 20`、`cellTypes`、`states`を持つ。`states`の各要素に状態名`name`と20行×10列の`cells`を記述し、発火順に並べる。1状態でも3状態以上でも登録できる。
3. 各状態には固定ブロックと、消去に使うTをちょうど4マス記す。Tは4方向いずれかのT字形である必要がある。Tがある行をすべてFull T-spinで消す形式を対象とし、消去行・Tの向き・空き必須マスをコードへ別途転記する必要はない。
4. `packages/core/templates.ts`でJSONをimportし、`templateDefinitions`にJSONの内容と固定ID、必要なら音声ファイル名を登録する。
5. 成立例・反転例・別の行を消した際の位置更新・似ているが成立しない例をテストする。

```ts
import dtCanon from '../../src/templete/DT canon/DT canon_new.json' with { type: 'json' };

export const templateDefinitions: TemplateDefinition[] = [
  { ...dtCanon, id: 'dt-canon', voice: 'DT_canon1.mp3' },
];
```

各状態は、消去前後の盤面を同じ10列×20行の座標系で記述する。初期配置の平行移動と反転を全状態に引き継ぎ、JSONに記録された上端の差で次状態の位置を求める。前状態の上端を消す場合や、次状態の横幅・上端が変わる場合も、消去後の盤面の該当位置を照合する。追跡中に型の外側の行を消した場合や、おじゃまがせり上がった場合は、その移動も引き継ぐ。

起動時に寸法、セル値、状態名、Tのマス数と形を検証する。不正な定義はエラーにし、テンプレートを追加したら`npm run check`で確認する。

DTフォルダーに残すファイルは`DT canon_new.json`と`DT_canon1.mp3`。成立時の表示名はJSONの`name`（DT canon）、デバッグ欄はテンプレート名と各状態の`name`（DT canon / 状態1・状態2）を使う。MP3は表示名と同じフォルダーから、定義の`voice`で指定したファイル（省略時は表示名と同名）を取得する。通常起動時に全テンプレートの音声をダウンロードせず、最初の消去で次段階に進んだ音声だけ先読みする。先読み失敗を毎フレーム再試行せず、成立時に再取得する。1状態のテンプレートは成立時に取得する。消去SEのRENによるピッチ変更は、テンプレートのボイスには適用しない。

## 計算量とブラウザー計測

各行を10ビットの整数に変換し、必要ブロックと空き必須マスをAND演算で比較する。テンプレートのマスク・左右反転・消去行は起動時に一度だけ作る。名前参照はMapで取得する。

毎設置の初期形走査は概ね`テンプレート数 × 2方向 × 配置可能な行数 × 配置可能な列数 × 型の高さ`。候補の追跡では保存した位置だけを照合する。操作中の通常の移動・回転では連携判定を行わない。

以下は入口・内部の空き条件と新JSON形式への対応を追加する前の測定値。2026-09-09、Intel Core i9-11900K／Linux／Chromium 153.0.8010.12で計測。DTのコンパイル済みパターンを複製し、末尾行だけが不一致の盤面で、消去前後の全位置走査を含む設置判定を測った。各条件20回のウォームアップ後、10回ずつ15バッチを計測。値は1判定あたりのバッチ平均の中央値。

| 登録件数 | 通常CPU  | CPUを4倍低速に設定 |
| -------- | -------- | ------------------ |
| 1        | 0.030 ms | 0.010 ms           |
| 10       | 0.030 ms | 0.090 ms           |
| 100      | 0.210 ms | 0.870 ms           |
| 1,000    | 2.120 ms | 8.670 ms           |

小さい値はタイマーの分解能や実行時の最適化の影響を受けるため、1件の測定からCPU低速設定の優劣を判断できない。1,000件・4倍低速時のバッチ平均の95パーセンタイルは10.000 ms。単発の最悪停止時間を示す値ではない。描画・デバッグ欄の別走査・音声デコード・通信・端末固有の負荷は含まない。CPUの低速設定は実スマホでの測定の代わりにはならない。

数個〜数十個を追加する用途には余裕がある見込み。数百件も今回の条件では小さいが、1,000件・低速端末では60 FPSの1フレーム約16.7 msに対して無視できない負荷になる。大幅に増やす場合は実機で再計測し、共通する行マスクによる候補の事前絞り込みなどを検討する。

再計測は開発サーバーを起動して次を実行する。

```sh
npm run dev -- --port 5179
# 別ターミナルで実行（JSON形式で結果を出力）
node scripts/benchmark-templates.mjs http://127.0.0.1:5179
```
