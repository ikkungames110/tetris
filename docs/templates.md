# テンプレート連携の検知

## developのデバッグ表示

盤面上の簡単な「DEBUG / 最終検知」欄に、初期形が一致した時点で`DT canon 検知`とプレイヤー・左端の列・上端の行・反転の有無を表示する。指定のDoubleを消した後に次の地形が一致すると、`DT canon2 検知`に更新する。行・列は画面左上を1として数える。操作中のミノは照合に含めない。

別の行の消去などで検知位置が変わった場合も表示を更新する。消去後も最後の検知を残し、ゲーム開始・リセット・新ラウンドで`未検知`に戻す。「最終検知」は履歴なので、形がなくなっても表示は残る。形の検知だけではボイスは再生しない。

デバッグ欄は固定盤面または連携の段階が変わった時だけ再計算し、同じ内容のオンラインスナップショットでは走査を省略する。

`develop`の変更は`main`のみを対象とする本番公開ワークフローでは公開されない。ローカルで`npm run dev`を実行して確認する。

## Double→Tripleの成立判定

`src/templete/DT canon/`の`DT_canon1.json`と`DT_canon2.json`を段階別の地形として使う。

1. DT canon（5列×7行）の必要ブロックを検知する。
2. その形の**下から2・3行目**をFull T-spin Doubleで消す。
3. 消去による移動後の同じ位置・向きにDT canon2（4列×5行）の必要ブロックがあることを確認し、次の段階へ進む。
4. DT canon2の**下から1・2・3行目**をFull T-spin Tripleで消したら、「DT canon」の文字・ボイスを出す。

下からの行番号は、各形の最下行を1とする。元の20行JSONではDoubleが17・18行目、Tripleが17・18・19行目に相当する（こちらは0始まり）。DT canon2だけを組んでも、先行する指定のDoubleの記録がなければDT canon演出にはならない。

Doubleは通常の「T-SPIN DOUBLE」、Tripleの消去SEは通常のものを残す。エンドレス・40LINE・オンライン両席・リプレイに対応する。Perfect Clearが成立する場合は従来どおりそちらを優先する。

## 形の照合と位置の追跡

- JSONの`1`は色に関係なく必要な固定ブロック。上部の入口3マス（各段階の左上基準で`[1,0]`・`[1,1]`・`[2,1]`）を`empty`として空き必須にし、入口まで埋まった地形の誤検知を抑える。それ以外の追加ブロックは許可し、実際のFull T-spin判定と指定行の消去で段階を進める。
- 左右移動・高さの違い・左右反転に対応する。段階ごとの幅が違っても、両形を含む共通の幅を基準に反転する。DT canon2は初期形より右端1列が狭いため、反転時は表示する左端が1列右へ移る。
- **毎設置、消去後の固定盤面を走査して初期形の場所を更新する。** 発火時は消去前の盤面から今回固定したミノを除き、初期形を再確認する。
- Double後は位置・向き・段階を保持し、毎設置その位置のDT canon2を再確認する。消去しない設置は許可し、必要なブロックが残っていれば保持する。
- 形全体の上側・下側にある別の行を消しても段階を解除せず、消去による行のずれを補正する。形の範囲内で指定外の行を消した場合や、指定行をFull T-spin以外で消した場合は次段階の候補を解除する。
- おじゃまのせり上がりでも位置を補正し、新ラウンドでは解除する。
- 同時追跡は最大32候補／プレイヤーで、Double後の候補を優先する。発火時の初期形の再検知はこの保存件数の上限に依存しない。テンプレート登録数自体の上限ではない。

表示・音声の情報だけを追加し、攻撃力や乱数・勝敗判定には使わない。候補と成立名はオンラインの検証済みスナップショットで共有し、既存リプレイの状態ハッシュからは除外する。初期形の段階も共有するため、通信プロトコルはバージョン4に更新した。

## テンプレートの追加

1. `src/templete/<表示名>/`に段階別のJSONとMP3を置く。PNGは確認用で、判定やブラウザー配信には使わない。
2. `packages/core/templates.ts`でJSONをimportし、`templateDefinitions`に固定ID・表示名・`stages`を登録する。
3. 各段階に`pattern`（その段階のJSON）、`spin`、`rowsFromBottom`（最下行を1とする消去行）を指定する。必要なら`empty`に空き必須の相対座標を指定する（左右反転前の共通矩形の左端・各段階の上端が基準）。
4. 成立例・反転例・別の行を消した際の位置更新・似ているが成立しない例をテストする。

```ts
stages: [
  { pattern: dtCanon, spin: 'full', rowsFromBottom: [3, 2] },
  { pattern: dtCanon2, spin: 'full', rowsFromBottom: [3, 2, 1] },
];
```

各JSONの横座標は共通の基準で配置する。次段階の上端は、前段階の上端を行消去で移動させた位置として照合する。上端自体を消す型や、次段階の上端を別の位置にする型を追加する場合は、段階間の位置対応を拡張する必要がある。

DTのファイル名は`DT_canon1.json`・`DT_canon1.png`・`DT_canon1.mp3`、`DT_canon2.json`・`DT_canon2.png`。表示名は従来どおりDT canon / DT canon2とする。MP3は表示名と同じフォルダーから、定義の`voice`で指定したファイル（省略時は表示名と同名）を取得する。通常起動時に全テンプレートの音声をダウンロードせず、最初の消去で次段階に進んだ音声だけ先読みする。先読み失敗を毎フレーム再試行せず、成立時に再取得する。消去SEのRENによるピッチ変更は、テンプレートのボイスには適用しない。

## 計算量とブラウザー計測

各行を10ビットの整数に変換し、必要ブロックと空き必須マスをAND演算で比較する。テンプレートのマスク・左右反転・消去行は起動時に一度だけ作る。名前参照はMapで取得する。

毎設置の初期形走査は概ね`テンプレート数 × 2方向 × 配置可能な行数 × 配置可能な列数 × 型の高さ`。候補の追跡では保存した位置だけを照合する。操作中の通常の移動・回転では連携判定を行わない。

以下は入口の空き条件を追加する前の測定値。2026-09-09、Intel Core i9-11900K／Linux／Chromium 153.0.8010.12で計測。DTのコンパイル済みパターンを複製し、末尾行だけが不一致の盤面で、消去前後の全位置走査を含む設置判定を測った。各条件20回のウォームアップ後、10回ずつ15バッチを計測。値は1判定あたりのバッチ平均の中央値。

| 登録件数 | 通常CPU  | CPUを4倍低速に設定 |
| -------- | -------- | ------------------ |
| 1        | 0.030 ms | 0.010 ms           |
| 10       | 0.030 ms | 0.090 ms           |
| 100      | 0.210 ms | 0.870 ms           |
| 1,000    | 2.120 ms | 8.670 ms           |

小さい値はタイマーの分解能や実行時の最適化の影響を受けるため、1件の測定からCPU低速設定の優劣を判断できない。1,000件・4倍低速時のバッチ平均の95パーセンタイルは10.000 ms。単発の最悪停止時間を示す値ではない。描画・デバッグ欄の別走査・音声デコード・通信・端末固有の負荷は含まない。CPUの低速設定は実スマホでの測定の代わりにはならない。

数個〜数十個を追加する用途には余裕がある見込み。数百件も今回の条件では小さいが、1,000件・低速端末では60 FPSの1フレーム約16.7 msに対して無視できない負荷になる。大幅に増やす場合は実機で再計測し、共通する行マスクによる候補の事前絞り込みなどを検討する。

再計測は開発サーバーを起動して次を実行する。

```sh
npm run dev -- --port 5179
# 別ターミナルで実行（JSON形式で結果を出力）
node scripts/benchmark-templates.mjs http://127.0.0.1:5179
```
