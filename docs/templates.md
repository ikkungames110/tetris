# テンプレート連携の検知

## developのデバッグ表示

盤面上の簡単な「DEBUG / 最終検知」欄に、形が一致した時点で`DT canon 検知`とプレイヤー・左端の列・上端の行・反転の有無を表示する。行・列は画面左上を1として数える。消去前の固定ブロックだけで照合し、操作中のミノは含めない。消去後も最後の検知を残し、ゲーム開始・リセット・新ラウンドで`未検知`に戻す。

この実験用表示は、既存のDouble→Tripleの成立判定から独立している。形が検知されるのに発火しない場合は、消去行やミノ位置・順序の条件を切り分けて調べられる。形の検知だけではボイスは再生しない。

固定盤面の各位置を調べるが、盤面のビット列が変わった時だけ走査する。オンラインの同一内容のスナップショットでも走査を省略する。後述の速度表は既存の消去時判定の計測であり、このデバッグ用全位置走査の測定値ではない。

`develop`の変更は`main`のみを対象とする本番公開ワークフローでは公開されない。ローカルで`npm run dev`を実行して確認する。

## Double→Tripleの成立判定

`src/templete/DT canon/` のJSON・PNG・MP3を使い、該当する形でT-spin Double→T-spin Tripleを消したとき、最後の表示・ボイスを「DT canon」に置き換える。Doubleは通常の「T-SPIN DOUBLE」、Tripleの消去SEは通常のものを残す。エンドレス・40LINE・オンライン両席・リプレイに対応する。

## 形と消去の条件

- JSONの`1`は色に関係なく必要な固定ブロック。移動中のミノは形の照合から除外する。
- ブロックを含む最小矩形（今回5列×7行）を取り出し、左右反転・左右移動・高さの違いに対応する。
- `0`をすべて空き必須にはしない。Tミノの入る4マスを各段階の`mino`で空き必須に指定し、それ以外には追加のブロックを置ける。図の周囲を埋めてラインを完成させても認識する。
- 最初のDoubleの固定・消去時に、消す行とTミノの位置から型の位置を特定し、必要ブロックと空きマスを確認する。この時点で形が一致すれば、事前の毎フレーム検知は不要。
- 消去前の図で上から0・1行目がDouble、2・3・4行目がTriple。元の20行JSONでは13・14行目、15・16・17行目に対応する（すべて0始まり）。下2行の支えも形の照合に含める。
- Double後は位置・向き・次の段階を保持する。同じ形の指定した行・Tミノの位置でFull T-spin Tripleになったときだけ成立する。
- 消去しない別ミノの設置は許可する。別のライン消去、必要な空間が埋まる設置、指定外のスピンは候補を解除する。おじゃまのせり上がりでは位置を補正し、新ラウンドでは解除する。
- 複数候補が同時に成立する場合は登録順を優先する。同時追跡は最大32候補／プレイヤー。テンプレートの登録件数そのものの上限ではない。

表示・音声の情報だけを追加し、攻撃力や乱数・勝敗判定には使わない。候補と成立名はオンラインの検証済みスナップショットで共有し、既存リプレイの状態ハッシュからは除外する。Perfect Clearが成立する場合は従来どおりそちらを優先する。

## テンプレートの追加

1. `src/templete/<表示名>/` に同名のJSON・MP3を置く。PNGは確認用で、判定やブラウザー配信には使わない。
2. `packages/core/templates.ts` の`templateDefinitions`にJSONをimportして、固定ID・表示名・消去順を登録する。
3. 各段階に`spin`、消去する`rows`、固定するミノ4マスの`mino`を指定する。座標は最小矩形の左上からの相対座標で、消去前の元の図を基準とする。消去による行の移動と左右反転はコンパイル時に計算する。
4. 成立例・反転例・似ているが成立しない例をテストする。

JSONの形だけから「どの順番でどの行を消すか」は確定できないため、消去順は明示的に登録する。現方式は元の図にある空間を順に使う連携向け。途中で消えた領域に新しい型を作り直す連携は、段階別の形の定義を拡張する必要がある。

MP3のURLは同名フォルダーから取得する。通常起動時に全テンプレートの音声をダウンロードせず、最初の消去で候補になった音声だけ先読みする。先読み失敗を毎フレーム再試行せず、成立時に再取得する。消去SEのRENによるピッチ変更は、テンプレートのボイスには適用しない。

## 計算量とブラウザー計測

各行を10ビットの整数に変換し、必要ブロックと空きマスをAND演算で比較する。テンプレートのマスク・左右反転・消去後の段階は起動時に一度だけ作る。画面描画時の名前参照はMapで取得する。

判定が必要な設置では、盤面のビット化が40×10セル、登録候補の照合が概ね`テンプレート数 × 2方向 × 型の高さ`。消去行と固定したミノから位置を決めるため、盤面の全位置を総当たりしない。通常の移動・回転では照合せず、候補がない通常設置も即座に返る。

2026-09-08、Intel Core i9-11900K／Linux／Chromium 153.0.8010.12で計測。DTのコンパイル済みパターンを複製し、末尾行だけが不一致の盤面で全件を調べた。各条件200回のウォームアップ後、100回ずつ30バッチを計測。値は1判定あたりのバッチ平均の中央値。

| 登録件数 | 通常CPU  | CPUを4倍低速に設定 |
| -------- | -------- | ------------------ |
| 1        | 0.005 ms | 0.007 ms           |
| 10       | 0.011 ms | 0.014 ms           |
| 100      | 0.036 ms | 0.123 ms           |
| 1,000    | 0.292 ms | 0.815 ms           |

1,000件・4倍低速時のバッチ平均の95パーセンタイルは1.549 ms。単発の最悪停止時間を示す値ではない。計測は照合処理のみで、描画・音声デコード・通信・端末固有の負荷を含まない。CPUの低速設定は実スマホでの測定の代わりにはならない。

数個〜数十個は十分な余裕があり、同規模の型なら数百件も現方式で対応できる見込み。1,000件でも今回の条件では60 FPSの1フレーム約16.7 msに対して小さいが、大きな型や多数の段階、古い端末が対象になった時点で再計測する。さらに増やす場合は、最初の消去種別による事前分類や共通マスクの共有が次の改善候補になる。

再計測は開発サーバーを起動して次を実行する。

```sh
npm run dev -- --port 5179
# 別ターミナルで実行（JSON形式で結果を出力）
node scripts/benchmark-templates.mjs http://127.0.0.1:5179
```
